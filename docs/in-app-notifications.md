# Independent in-app notifications

The in_app channel supports new_filing for issuer, insider and institutional-filer follows, plus insider_transaction and cluster for issuer/person follows. It is independent of email: rule activation is the explicit opt-in and never enables email or push. Institutional-change and news in-app triggers and push delivery remain unsupported. Email rules, delivery history and existing alert-event read state remain separate.

## Rules and quotas

Use the existing POST /api/v1/alert-rules contract with channels=["in_app"], trigger=new_filing, insider_transaction or cluster, an owned follow_id and frequency=daily_digest or instant. The default frequency remains daily_digest. Create one channel at a time; arrays containing both email and in_app are rejected. Each channel has a separate record/configuration/revision, but the same (follow_id, trigger) pair counts once toward the logical rule quota. Email and in-app rules for that pair share one slot. Paused drafts count; a logical slot is released only after every channel in that pair is archived. Channel and trigger changes require creating a separate record. Recreating an existing channel is idempotent.

Free accounts retain three logical rules and daily-digest timing only. Pro may use instant delivery. Rule APIs now expose meta.rule_quota.used and shared_across_channels=true; paginated row counts still count channel records. supported_channels includes email and in_app; in_app_supported_triggers lists new_filing, insider_transaction and cluster. Existing email activation still requires email consent and a time zone. Daily in-app activation requires a valid IANA time zone via /api/v1/me/notification-preferences, with no email consent. Instant Pro in-app rules require neither an email preference nor a time zone.

## Matching and publication

The existing commit-deferred EvaluateAlertsJob invokes the matcher after ingestion. SQL resolves follow membership using the same source-specific matching predicates as email. Supported sources are parsed Form 4 / 4/A and 13F-HR / 13F-HR/A / 13F-NT filings. Filings must have been accepted at or after rule activation and no later than evaluation. Reprocessing a pre-activation historical filing never creates a notice for a newly enabled rule. A partial unique rule/filing index makes new-filing evaluation idempotent; transaction lines have a separate key described below.

Instant notices are eligible at capture time and published through the same policy gate. Daily notices become eligible at the next 07:00 in the configured time zone, including daylight-saving transitions; capture exactly at 07:00 uses the following day. The captured due time and time zone are stored. Pending rows are never included in read APIs.

Before publication SQL rechecks rule activation, archive/revision/frequency, current follow membership, parsed source visibility, current time zone for digest items, logical quotas and verified Pro entitlement for instant delivery. A daily item's captured zone must still match the current preference. Pending rows remain stored when blocked; pausing/resuming resets the rule's enable window so its older captured notices cannot replay. Changes to conditions/frequency require pausing under the existing rule rules.

PublishInAppNotificationsJob runs on the alerts queue once per minute, independently of SEC polling and email consent. Each call publishes at most 1,000 due rows; rule locks with SKIP LOCKED allow concurrent publishers without overwriting a publication timestamp. Ingest-triggered publication is scoped to that filing. Additional due rows drain in later batches. These limits and polling do not establish a measured two-minute latency guarantee. No worker was started, data reprocessed or real notification transport activated by this increment.

## Private APIs

- GET /api/v1/notifications accepts unread=true/false, sort=published_at/-published_at, limit (default 50, maximum 100) and cursor. Signed cursors bind account, filters, publication snapshot and notification ID ceiling. Rows contain id, rule_id, trigger, channel, entity, publication/read/creation timestamps and SEC provenance including accession, sec_url, filed_at, accepted_at, ingested_at and data_age_days.
- GET /api/v1/notifications/summary returns total_count, unread_count, read_count and as_of for visible owned notices. It accepts no filters.
- POST /api/v1/notifications/:id/read requires CSRF and marks a visible owned notice once. Repeated calls preserve the original read_at; foreign, pending or unavailable-source IDs return 404.
- POST /api/v1/notifications/read-all requires CSRF and captures visible membership and updates its unread rows in one SQL statement, reporting the maximum captured ID. It returns updated_count, through_id and as_of. Later publications remain unread.

All routes require authentication and return no-store responses. Malformed filters/IDs return 400 and existing shared rate limits apply. Reads do not publish notices or enqueue delivery. Read state is live: changing it can change unread membership on a continuation, so refresh after acknowledgement. Email consent, email status and email read states are not altered.

Published notices remain history when a rule is paused/archived or a follow removed, subject to source validity checks. Each is explicitly a historical_filing_notice, not a claim of current effective holdings or current transaction state. For new_filing, originals and later amendments remain separate notices with their original provenance. Transaction notices are excluded when their source filing is superseded. If a source is no longer parsed or is not visible by the request snapshot, it is excluded before counting/pagination. This does not infer an amendment's economic meaning. The UI can follow accession/sec_url for source evidence.

## Storage and verification

in_app_notifications stores rule/filing foreign keys, rule revision, captured frequency/time zone, available_at, published_at, read_at and timestamps. It does not copy or overwrite as-reported filing values. Account deletion removes owned notification records before deleting rules; filing records remain. The transaction extension changes this notification table only; no raw filing/transaction schema or reported values are changed. No gem, provider request, enrichment or seed data is needed.

Local tests cover digest/instant gates, shared quotas, both filing families, idempotency, local/DST cutoffs, bounded publication, pause/revision/membership/time-zone/plan changes, historical amendments, source exclusion, private cursors, read/read-all, account deletion and email/scheduler regressions. There is no WebSocket, SSE stream, frontend integration or push transport in this increment.

## Insider transaction alerts

Create an in_app rule with trigger=insider_transaction for an owned issuer/person follow. Conditions reuse the existing transaction alert normalizer and SQL: direction, transaction-code list, role, open_market/administrative type, security_table and min_value. Code lists are normalized; malformed/unknown fields are rejected. A fund-scoped transaction rule is invalid. Free daily timing, Pro instant gating, email independence and logical cross-channel quotas are unchanged. A new_filing rule and a transaction rule are different logical slots; email and in_app variants of the same transaction rule share one slot.

Each matched transaction line yields its own notification. Joint reporting-owner copies are selected with the existing rule/line DISTINCT ON policy: prefer the first matching owner by owner sequence and ID, including a later owner if the role/person condition requires it. The stable deduplication key is (rule_id, filing_id, security_table, txn_seq), not CUSIP or reporting-owner row ID. This keeps multiple transaction lines and the two tables separate while preventing owner-copy duplicates across retries. The selected insider_transaction_id retains the actual matched owner evidence. Capture is SQL INSERT SELECT with a partial unique index; rule/filing uniqueness still applies to new_filing notices.

The response trigger reflects the stored event type and adds transaction, using the existing normalized transaction serializer with exact reported decimals, direction/code, role, owner/row sequence, missing/suspect-value flags and SEC provenance. transaction is null for new_filing. Missing or suspect prices cannot satisfy min_value, including a zero threshold. A reported zero price remains a reported zero rather than a substituted missing value. Administrative and derivative rows are available when the conditions allow them; no inferred code or price is created.

Publication, lists, summary, individual read and read-all share SQL transaction-source validity: the selected row must match the stored filing/table/sequence and the source must remain in the effective parsed Form 4 set at the query snapshot. A superseding parsed amendment suppresses queued originals and excludes previously published originals from the visible inbox. Stored notifications, read timestamps and original filings remain intact; the amendment's lines may produce separate notifications if the rule matches. This differs intentionally from a historical new_filing notice, which still reports that the original filing occurred. Unavailable/mismatched source references are excluded before counts and pagination.

Notification cursors now include a filing ID ceiling as well as notification bounds, preventing a newly ingested backdated amendment from changing source selection within an existing continuation. Existing pre-extension notification cursors must be restarted (400); notification IDs and read state are unchanged. Current fresh reads can reflect new amendments. Rule changes still require pausing; pre-activation filings never replay.

The forward-only local migration adds event_type (existing rows default to new_filing), the selected transaction FK and table/sequence identity. It replaces the old unique index with source-specific partial indexes and adds source-shape checks. Model validation rejects mismatched transaction references; shared read/publication policy also guards bulk-write corruption. Automatic rollback deliberately raises IrreversibleMigration: multiple transaction notices cannot fit the former one-row-per-rule/filing key. Any reversal needs a separate data-preserving migration plan, not deleting notification history.

Generated/local fixtures test typed conditions, person/issuer matching, a later qualifying joint owner, same-filing multiple lines/tables, retry idempotency and database uniqueness, missing/suspect values, daily/instant gates, source mismatches, amendment suppression, historical record retention, cursor stability and email compatibility. The existing commit-deferred evaluator and bounded publisher remain in use; no new scheduler, real delivery, SEC request or data reprocessing was activated.

## Cluster alerts

The in_app channel now supports trigger=cluster on issuer/person follows using the existing direction, min_insiders and min_value conditions. Direction is purchase or sale; min_insiders must be an integer from the published methodology minimum (currently three) through 1,000. A value threshold requires a complete total: incomplete clusters keep total_value=null and a separate known_value_subtotal, and cannot satisfy min_value. Fund-scoped cluster rules and unsupported/malformed conditions are rejected. Free daily timing, Pro instant gates, rule activation and shared logical quotas are unchanged. No email consent is required.

Matching reuses ClusterAlertMatcher with a channel argument (default email), including its 14-day SEC-acceptance window, first-listed canonical transaction policy and delayed-ingestion handling. A followed joint owner can match through the canonical transaction's owner copies without adding a participant. Administrative/derivative lines cannot inflate cluster membership. Immutable InsiderClusterSnapshot evidence is shared across matching rules and channels; no snapshot is rewritten. The deduplication key is (rule_id, insider_cluster_snapshot_id). Re-evaluating the same window state creates no additional notification, while a changed membership set or distinct rolling window produces a separate immutable event state, matching existing email semantics.

A delayed earlier filing can reveal a later anchored cluster. The notification's filing_id and root SEC provenance come from the snapshot's primary_filing_id, not necessarily the filing that triggered evaluation. Ingest publication includes these primary filings so an eligible instant notice does not wait for the cron publisher.

Notification responses add cluster (null for other triggers) with the existing cluster serializer's issuer, direction, window dates, frozen window length, participant/transaction counts, total/subtotal/unknown-value coverage, canonical transaction/activity IDs, insider names and every source filing's provenance. observed_at and definition_minimum_insiders preserve the original observation/definition. Batch initialization loads all selected snapshots and their filing evidence together, avoiding a per-notification source query. These are as-observed filing facts, not an Activity Score or a claim that historical coverage is complete.

Publication and every inbox/read/count operation require the snapshot's primary filing to match the stored notification and every constituent filing to remain in the effective parsed Form 4 set at the query snapshot. Source checks also verify that all captured transaction IDs still resolve to canonical non-derivative rows of the snapshot's issuer/direction and belong to its filing set. A failure or superseding amendment of any constituent invalidates the cluster, even when its primary filing is unchanged. Queued invalid clusters cannot publish; published invalid clusters are excluded before counting, pagination and acknowledgement. Stored notification/read history and immutable snapshots remain intact. Existing source-bound cursor semantics apply; no additional cursor version change is introduced by this extension.

The local forward-only migration adds insider_cluster_snapshot_id and a partial unique rule/snapshot index to in_app_notifications, and extends its source-shape constraint. Clusters cannot also carry a transaction pointer/table/sequence. Existing filing/transaction notices retain their keys and nullable cluster reference. No existing snapshot, raw filing or transaction value is rewritten. Automatic rollback is intentionally unavailable to protect cluster notification history; a reversal requires a separately reviewed data-preserving plan.

Local tests cover API validation, email independence, plan gates, shared snapshots/quotas, retries and database uniqueness, joint-owner handling, sale/value conditions, missing values, delayed primary filings, late membership/window states, local digest timing, any-member amendment/failure suppression, read-state exclusion and malformed source references. Email cluster and other in-app regressions remain in the suite. No new scheduler, provider request, seed data, real email/push delivery or deployment is activated.
