# OAuth identity management foundation

External sign-in and linking are not implemented. No Google credentials, redirect, token exchange, verifier, callback or provider request is activated. The identity registry is an empty local foundation for later verified callbacks; it does not support signing in. No new dependency was added.

`GET /api/v1/me/oauth-identities` requires an existing session and returns private, no-store `data` entries with id, provider and linked_at. Metadata reports linking_enabled=false, sign_in_enabled=false and unlinking_enabled=true. The only reserved provider is google; at most one identity per provider/account is permitted. Provider subjects, email claims and tokens are never returned. Reads accept no query parameters and do not create records. The list is bounded by the provider/account unique index and single-provider constraint.

`DELETE /api/v1/me/oauth-identities/:id` requires the session cookie, browser CSRF token and JSON current_password. A successful unlink returns the existing session-response envelope containing the user and a fresh csrf_token. It removes only the owner's identity, revokes every old session and rotates to a new current session in one transaction. Session-bound push registrations are removed by existing cascades. Clients must replace their CSRF token. Missing/foreign identities return 404 after password verification; incorrect passwords return 401 REAUTHENTICATION_REQUIRED. Attempts are limited to ten per account per three minutes, alongside shared API limits. Unknown fields, missing passwords and malformed identifiers return 400. There is no browser-supplied identity registration endpoint.

The oauth_identities table stores user_id, provider, subject and timestamps. Global provider/subject uniqueness prevents identity reassignment; per-user/provider uniqueness prevents ambiguous local associations. Model ownership fields are read-only. Account deletion removes identities through the association and database cascade. No access tokens, refresh tokens, provider passwords or email claims are stored. Subjects use a local maximum of 255 characters; this is an application storage constraint.

The current app requires a local password. Requiring that password for unlinking preserves a usable local login method. A future passwordless flow must change this policy explicitly before it can create accounts without passwords. Email equality must never silently link an external identity to an existing account.

The next OAuth increment needs a reviewed provider-verification integration and configuration boundary, explicit authenticated linking intent, callback/request correlation, replay prevention and tests before any external identity can be persisted through the application. Those requirements are unfinished here. Tests populate synthetic identities directly; no real identity or user data is seeded.
